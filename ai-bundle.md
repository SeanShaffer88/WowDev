# WowDev — World of Warcraft Addon Development Knowledge Base

## TL;DR

A complete, self-contained knowledge base for developing World of
Warcraft addons, written for AI agents and humans. It covers the WoW
API and WoW's Lua 5.1 dialect, the client flavors and their interface
numbers (Retail, Classic Era, the progression Classic clients, and WoW
Forever), libraries and frameworks, editors and tools, testing,
packaging and distribution, and the communities where addon developers
actually get help — plus the working material itself: copy-and-start
**templates**, three complete **example addons**, a scaffolder and a
static validator in **tools**, and quick **reference** tables. Every
external resource named here was verified against its live source on
2026-11-17; anything that could not be verified is marked
**Unverified** rather than repeated as fact.

## The ground-truth hierarchy

When sources disagree, this order wins:

1. **The client itself** — Blizzard's own UI source for the exact
   client you target (`Gethe/wow-ui-source`, one branch per flavor)
   and the in-game `/api` documentation (`Blizzard_APIDocumentation`).
2. **Warcraft Wiki** (warcraft.wiki.gg) — the living community wiki,
   including its per-patch "API changes" pages.
3. **This repo** — a distillation of 1 and 2 plus verified third-party
   material.
4. **Everything else** — Wowpedia's Fandom copy (frozen in 2023),
   wowprogramming.com (frozen around Warlords of Draenor), forum posts,
   and model memory. Useful for history and fundamentals, never as
   proof that an API exists in a current client.

## The flavors at a glance

**WoW Forever is the primary target of this repo** (it is the client
the maintainer develops for); the other flavors are covered in full
because porting between them is half the work.

| Flavor | Interface (checked 2026-11-17) | wow-ui-source branch |
|---|---|---|
| WoW Forever | **16001** | `forever` |
| Retail | 120100–120107 range | `live` |
| Classic Era | 11508 / 11509 | `classic_era` |
| TBC Classic | 20505 / 20506 | `classic` (progression) |
| Wrath Classic | 30405 | `classic` |
| Cata Classic | 40402 | `classic` |
| MoP Classic | 50503 / 50504 | `classic` |
| Classic 3.80.x ("Timewalking") | 38002 | `classic` |

Interface numbers are how the client decides whether an addon loads at
all: a `.toc` whose `## Interface:` does not match the client is marked
out of date and never loads — no error, no warning in-game, just a dead
addon. Full treatment: [`docs/04-flavors-and-interface-numbers.md`](docs/04-flavors-and-interface-numbers.md).

## How an AI should use this repo

1. Read [`AGENTS.md`](AGENTS.md) — the non-negotiable rules (never
   invent an API, flavor first, Lua 5.1 subset only).
2. Identify the **target flavor and interface number** before writing
   any code ([`docs/04`](docs/04-flavors-and-interface-numbers.md)).
3. Start from [`docs/01-addon-anatomy.md`](docs/01-addon-anatomy.md)
   (.toc, load order, SavedVariables) and
   [`docs/02-lua-in-wow.md`](docs/02-lua-in-wow.md).
4. Check every API function, event, and widget method against
   [`docs/03-api-events-and-widgets.md`](docs/03-api-events-and-widgets.md)'s
   sources — Warcraft Wiki for the flavor, or the matching
   wow-ui-source branch.
5. Prefer a library over hand-rolling
   ([`docs/05-libraries-and-frameworks.md`](docs/05-libraries-and-frameworks.md)).
6. Start from a template or example instead of a blank page:
   [`templates/`](templates/) (minimal + Ace3 skeletons, release
   workflows), [`examples/`](examples/) (three complete addons), and
   the scaffolder in [`tools/`](tools/).
7. Test per [`docs/08-testing-and-debugging.md`](docs/08-testing-and-debugging.md);
   package and release per
   [`docs/09-packaging-and-distribution.md`](docs/09-packaging-and-distribution.md)
   and [`checklists/addon-checklist.md`](checklists/addon-checklist.md).

# AGENTS.md — Instructions for AI agents writing WoW addons

You are using this repository as your knowledge base for creating World
of Warcraft addons. Follow these rules exactly.

## Non-negotiable rules

1. **Never invent API functions, events, widget methods, or CVars.**
   Every WoW API call you write must be traceable to one of: the
   Warcraft Wiki page for the target flavor, the matching branch of
   `Gethe/wow-ui-source`, or the in-game `/api` documentation
   (`Blizzard_APIDocumentation`). If you cannot trace it, do not write
   it — say it is **Unverified** instead. The WoW API is large,
   flavor-dependent, and changes every patch; a plausible-sounding
   function name is the single most common AI failure on WoW code.
2. **Flavor first.** Before writing code, state the target client and
   its interface number: Retail (1201xx), Classic Era (11508/11509),
   WoW Forever (**16001**), or a progression Classic client
   (`docs/04-flavors-and-interface-numbers.md`). A `.toc` with the
   wrong `## Interface:` never loads. Never write 11507 (or any Era
   number) into a Forever `.toc` — Forever is 16001.
3. **Lua 5.1 subset only.** WoW runs a subset of Lua 5.1 (client on
   5.1.1 since patch 2.0.1). No Lua 5.2+ features: no `goto`, no integer
   division `//`, no bitwise operators, no `table.unpack` (it is
   `unpack`), no UTF-8 library. When in doubt, the Lua 5.1 reference
   manual (https://www.lua.org/manual/5.1/) is the language ground
   truth, and Warcraft Wiki's Lua pages say what the client actually
   provides.
4. **Respect the restriction tags.** Wiki API listings tag functions
   (`#hwevent` = needs a real hardware event, `#noscript`, `#framexml`).
   Protected functions and secure templates have real rules — read
   `docs/03-api-events-and-widgets.md` before writing combat-relevant
   or action-button code. Taint is a correctness bug, not a warning.
5. **Never call `SetBackdrop` on a plain frame.** Plain frames do not
   have that method; use a frame created with the `BackdropTemplate`
   template (or mix `BackdropTemplateMixin` in first). This crashes on
   clients where the method is absent, WoW Forever included.
6. **Declare SavedVariables in the .toc** or they do not persist.
   Nothing outside the declared variables survives a logout.
7. **Start from the closest existing pattern.** An official Blizzard UI
   module in wow-ui-source, an Ace3-based addon, or the examples in
   this repo's docs outrank anything you generate from memory. Borrow
   structure; verify every API call anyway (rule 1).
8. **Prefer a maintained library over hand-rolling** (Ace3 for most
   needs — `docs/05-libraries-and-frameworks.md`), and embed libraries
   the standard way (LibStub + `.pkgmeta` externals at packaging time),
   not by pasting library code into the addon.
9. **Every addon ships four docs**: `README.md`, `FEATURES.md`,
   `DESCRIPTION.md` (store-listing copy), and `CHANGELOG.md`, plus a
   license file. Public docs contain only factual product
   documentation.
10. **Verify before declaring done.** Run
    `checklists/addon-checklist.md`. State plainly which checks ran
    in-game or in wowless and which could not be run — label those
    **Unverified** rather than claiming success. An addon that has
    never been loaded by its target client is not tested.

## Build order (always in this sequence)

1. Name the target flavor + interface number (rule 2).
2. Lay out the addon folder and `.toc` (`docs/01-addon-anatomy.md`).
3. Write the smallest loadable addon; confirm it loads with no errors.
4. Add features one at a time, checking each new API call against the
   ground-truth sources (rule 1) and testing in the target client.
5. Add SavedVariables, options, and localization as needed.
6. Package with the BigWigs packager or a plain zip
   (`docs/09-packaging-and-distribution.md`); run the checklist.

## Things that are always wrong

- An API function, event, or widget method that appears in no source
  for the target flavor.
- Lua 5.2+ syntax or standard-library calls in addon code.
- `## Interface:` copied from a different flavor's addon.
- SavedVariables used without being declared in the `.toc`.
- `SetBackdrop` on a frame not created with `BackdropTemplate`.
- Global-namespace pollution: addon code that creates unlocalized
  globals beyond its one addon table (it collides with other addons
  and spreads taint).
- Treating Wowpedia's Fandom pages or wowprogramming.com as evidence
  an API exists in a current client — both are frozen snapshots.
- Recommending wow.tools (shut down May 2025) or WowBench (defunct).

# 01 — Addon Anatomy

An addon is a folder in `Interface/AddOns/` containing a `.toc` file
with the **same name as the folder**, plus Lua and/or XML files. The
client reads the `.toc` at startup; everything else follows from it.

## The .toc file

The `.toc` (table of contents) is the addon's manifest. Metadata lines
start with `## Key: Value`; file lines list what to load, in order.

Essential keys:

| Key | Meaning |
|---|---|
| `## Interface: 16001` | The client interface version this addon targets. Must match the client or the addon is marked out of date and does not load. One per flavor — see [`04`](04-flavors-and-interface-numbers.md). The packager can generate per-flavor TOCs from `## Interface-[Type]:` lines ([`09`](09-packaging-and-distribution.md)) |
| `## Title: My Addon` | Display name in the addon list |
| `## Notes: ...` | Short description shown in the addon list |
| `## Author: ...`, `## Version: ...` | Shown in the addon list; the packager can substitute `@project-version@` for Version |
| `## SavedVariables: MyAddonDB` | Global variables persisted account-wide between sessions. **Undeclared variables do not persist.** |
| `## SavedVariablesPerCharacter: MyAddonCharDB` | Same, per character |
| `## Dependencies: OtherAddon` | Hard load-order dependency (older spelling `## RequiredDeps:` is also used); the addon will not load without it. Standalone framework addons (RGX-Framework, Foundry-1.0) are consumed this way |
| `## OptionalDeps: Ace3` | Load after these if present |
| `## LoadOnDemand: 1` | Do not load at startup; load via `LoadAddOn()` |
| `## X-Curse-Project-ID:`, `## X-WoWI-ID:`, `## X-Wago-ID:` | Distribution site IDs the BigWigs packager reads ([`09`](09-packaging-and-distribution.md)) |

Below the metadata, list files **one per line, in load order** —
typically libraries first, then core files, then modules, then XML.
Files load in exactly the order listed; a file that uses something
defined in a later file fails.

## Load order and lifecycle (the short version)

1. The client reads all `.toc` files and builds the addon list.
2. At login, each enabled addon's files execute in `.toc` order.
3. `ADDON_LOADED` fires when an addon's files have finished loading —
   the standard moment to initialize SavedVariables (they are loaded
   just before the addon's files run).
4. `PLAYER_LOGIN` fires after the world and all addons are in.
5. SavedVariables are written back at logout/reload.

## The addon namespace pattern

Every Lua file in an addon receives the same varargs: the addon name
and a shared table. The standard pattern, used by virtually every
maintained addon:

```lua
local addonName, addon = ...
addon.events = {}
```

Files share state through that one table instead of globals. Addons
that spray unlocalized globals collide with each other and spread
taint; keep exactly one global at most (usually none — the namespace
table is passed, not global).

## Lua vs XML

- **Lua** defines behavior: events, logic, most frame creation.
- **XML** defines frame structure declaratively (FrameXML style) and
  virtual templates. Blizzard's own UI uses both; most modern addons
  create frames in Lua and use XML rarely, mainly for templates.
- Both are listed in the `.toc`. XML files load their `Script` includes
  relative to the XML file's folder.

## Folder layout conventions

```
MyAddon/
  MyAddon.toc
  Core.lua
  Options.lua
  Modules/
  Libs/            (embedded libraries, usually filled by the packager)
  Locales/
  Media/           (textures must be BLP or TGA — see docs/07)
  README.md  FEATURES.md  DESCRIPTION.md  CHANGELOG.md  LICENSE
```

## Sources

- Warcraft Wiki HOWTOs (Getting Started collection):
  https://warcraft.wiki.gg/wiki/HOWTOs — includes "Create a WoW AddOn
  in 15 Minutes" and the saved-variables and slash-command guides.
- `Gethe/wow-ui-source`, matching branch — read any `Blizzard_*`
  addon's `.toc` for the pattern at production scale.

# 02 — Lua in WoW

WoW's scripting is **Lua 5.1** — the client was upgraded to Lua 5.1.1
in patch 2.0.1 (2006) — and only a **subset** of the official 5.1
specification is implemented (Warcraft Wiki, Lua page). The Lua 5.1
Reference Manual (https://www.lua.org/manual/5.1/) is the language
ground truth; Warcraft Wiki's Lua pages are the authority on what the
client actually provides.

## What that means in practice

- **5.1 semantics, not modern Lua.** `unpack` is global (there is no
  `table.unpack`); `loadstring` and `setfenv`/`getfenv` exist; string
  patterns are 5.1 patterns; numbers are doubles. Nothing from 5.2+:
  no `goto`, no `//`, no bitwise operators, no `utf8` library, no
  integer subtype.
- **The standard library is trimmed.** File I/O and OS facilities are
  largely absent — an addon cannot read or write arbitrary files; the
  only persistence is SavedVariables ([`01`](01-addon-anatomy.md)).
  The `debug` library is restricted. Verify any standard function
  against the wiki's Lua documentation before using it; the manual
  documents the *full* language, including parts the client omits.
- **WoW adds its own global functions and aliases** on top of Lua
  (string/table helpers and the entire UI API). Those live in the API
  documentation, not the Lua manual — see
  [`03`](03-api-events-and-widgets.md).

## Patterns that matter

- **Everything is a table.** SavedVariables, the addon namespace,
  frame objects, and library registries are all tables. Metatables
  provide the object model; Ace3 and the other frameworks in
  [`05`](05-libraries-and-frameworks.md) are table patterns all the
  way down.
- **Locals are fast and safe; globals are shared with everyone.** An
  unlocalized global is visible to every addon and to taint tracking.
  Cache hot globals as locals (`local pairs = pairs`) in performance-
  sensitive code.
- **Varargs carry the addon namespace**: `local addonName, addon = ...`
  at the top of every file ([`01`](01-addon-anatomy.md)).
- **Events drive everything.** There is no main loop you own; code
  runs at load time, on events, on frame updates (`OnUpdate`), and on
  timers. Long-running work in one call blocks the whole UI — spread
  heavy work across frames (this is the entire reason frame-budgeted
  task libraries exist).
- **Errors are Lua errors.** A runtime error in an event handler stops
  that handler, not the client. Enable script errors while developing
  ([`08`](08-testing-and-debugging.md)) or failures are silent.

## Common AI/author mistakes

- Writing Lua 5.4 idioms from general training data (`//`, `<close>`,
  `table.unpack`) — all invalid here.
- Assuming a standard-library function exists because the manual lists
  it (subset rule above).
- Forgetting that strings are immutable and patterns are not regex —
  WoW string patterns follow Lua pattern syntax, documented in §5.4.1
  of the 5.1 manual.
- Doing heavy work inside `OnUpdate` without throttling — it runs
  every frame.

## Learning Lua for WoW

- *Programming in Lua*, **2nd edition** (Ierusalimschy) — the edition
  that covers Lua 5.1 (the 1st edition covers 5.0 and is free at
  lua.org; the 5.1 manual is free too).
- "Introduction to Lua" — Warcraft Wiki / Wowpedia HOWTOs, a fast
  primer that explicitly targets WoW's 5.1.
- *Beginning Lua with World of Warcraft Add-ons* (Emmerich, 2009) —
  novice-to-advanced, WoW-specific throughout.

# 03 — The API, Events, and Widgets

## Where the API is documented (in trust order)

1. **In the client itself.** Blizzard ships `Blizzard_APIDocumentation`
   — the official, generated documentation for the C++-backed API —
   accessible in-game via the `/api` command, and mirrored inside
   `Gethe/wow-ui-source` as `Blizzard_APIDocumentationGenerated`.
2. **Warcraft Wiki** — https://warcraft.wiki.gg/wiki/World_of_Warcraft_API
   is the maintained community reference, organized by `C_*` namespace
   with signatures like
   `C_AddOns.GetAddOnInfo(name) : name, title, notes, loadable, reason, security, ...`.
   Classic flavors have a dedicated subpage (`World of Warcraft
   API/Classic`). Per-patch **API changes** pages are the migration
   source when a client version moves.
3. **Blizzard's own UI code** in wow-ui-source — when the wiki is
   ambiguous, how FrameXML actually calls the function is the answer.

The wiki's nav splits the surface into: WoW API, Lua API, FrameXML,
Widget API, Widget scripts, XML schema, Events, CVars, Macro commands,
Combat Log, Escape sequences, and Hyperlinks.

## Restriction tags — read them

Wiki listings tag functions with machine-readable restrictions:

- `#hwevent` — requires a hardware event (a real key press / click) to
  do its protected action.
- `#noscript` — not callable from addon scripts in the way the listing
  context implies.
- `#framexml` — implemented in FrameXML Lua rather than in C++.

Treating every listed function as freely callable is how addons end up
"blocked" in combat. Protected functions and actions (casting, moving,
targeting, action buttons) are governed by the **secure execution**
model: in combat lockdown, protected calls from tainted code fail.

## Taint in one paragraph

Code that originates from addons is *tainted*; when tainted code
touches secure objects or execution paths, the taint spreads, and the
client then refuses protected actions along that path ("Interface
action failed because of an AddOn"). The practical rules: don't modify
Blizzard objects' secure properties from addon code, don't store
values into secure frames' fields, use secure templates
(`SecureActionButtonTemplate` and friends) for anything clickable in
combat, and debug taint with the tools in
[`08`](08-testing-and-debugging.md). The secure template attribute
reference on wowprogramming.com is old but still the reference for
attribute semantics (the mechanism has not changed).

## Events

The event system is the addon's nervous system: frames register for
named events (`RegisterEvent`, `RegisterUnitEvent`) and receive them
in their `OnEvent` script handler. Key facts:

- Event names, payloads, and availability differ **per flavor and per
  patch** — check the wiki's Events page for the target client, and
  the API changes pages when porting.
- `ADDON_LOADED` and `PLAYER_LOGIN` structure most addon startup
  ([`01`](01-addon-anatomy.md)).
- Unit events only fire for units that exist; registering for a unit
  event with an invalid unit is a classic silent failure.

## Widgets (frames)

Frames and their subclasses (buttons, status bars, edit boxes,
scroll frames, cooldowns…) are created with `CreateFrame` in Lua or
declared in XML, and driven through widget methods and script handlers
(`OnEvent`, `OnUpdate`, `OnClick`, …). The Widget API and Widget
scripts pages on Warcraft Wiki are the reference. Two standing traps:

- **Backdrop:** never call `SetBackdrop` on a plain frame — create the
  frame with the `BackdropTemplate` template (or mix in
  `BackdropTemplateMixin`) first. Plain frames do not have the method
  on clients that enforce the split.
- **Scale/anchoring across flavors:** widget behavior details (e.g.
  which templates exist) differ between Retail and the Classic-family
  clients; the matching wow-ui-source branch shows what the target
  client's FrameXML actually ships.

## CVars, macros, combat log

- **CVars** (console variables) are documented on the wiki with
  defaults; addons read/write them via the CVar API, but many are
  protected or account-wide — check before touching.
- **Macro commands** and **secure conditionals** are their own
  documented surface on the wiki; addons generate macros but cannot
  execute protected actions outside the secure rules above.
- **Combat Log** events arrive as one high-volume event with sub-event
  payloads; parse defensively — the format is flavor-sensitive.

# 04 — Flavors and Interface Numbers

WoW is not one client. An addon targets a **flavor**, the `.toc`'s
`## Interface:` must equal that client's interface version, and the
API differs between flavors in ways that matter. Numbers below were
checked 2026-11-17 against the Ace3 project's own `.toc` (a production
multi-flavor addon) and the `Gethe/wow-ui-source` branch list.

| Flavor | Interface | wow-ui-source branch | Notes |
|---|---|---|---|
| Retail | 120100–120107 | `live` | PTR on `ptr`/`ptr2`, beta on `beta` |
| Classic Era | 11508, 11509 | `classic_era` | Era PTR on `classic_era_ptr` |
| WoW Forever | **16001** | `forever` | Custom 1.12-lineage client (game version 1.60.1) |
| TBC Classic | 20505, 20506 | `classic` | Progression Classic shares the `classic` branch |
| Wrath Classic | 30405 | `classic` | |
| Cata Classic | 40402 | `classic` | |
| MoP Classic | 50503, 50504 | `classic` | |
| Classic "Timewalking" 3.80.x | 38002 | `classic` | 2026 client whose API was aligned heavily toward Retail (see the liuwu0623 pack, docs/11) |

## The interface rule

The client compares `## Interface:` against its own version at load.
A mismatch marks the addon **out of date**; with "load out of date
addons" off (the default for most players), it simply never loads —
no Lua error, no message in the addon itself. Most "my addon does
nothing" reports are this.

- One `.toc` can serve several flavors when the packager generates
  per-flavor TOCs from `## Interface-[Type]:` lines
  ([`09`](09-packaging-and-distribution.md)).
- **Forever is 16001.** Any brief, template, or older addon that puts
  an Era number (11507 and friends) in a Forever `.toc` is wrong; the
  addon will be dead on arrival. This is field-proven, not theoretical.

## Per-flavor traps

- **API surface.** Retail has namespaces and widgets the Classic
  family lacks, and vice versa; Classic Era/Forever are closest to the
  1.12-era API with selective backports. Always check the flavor's own
  wiki pages and source branch ([`03`](03-api-events-and-widgets.md)).
- **Templates differ.** Which XML templates exist (including
  `BackdropTemplate` behavior) is a per-flavor fact — read the target
  branch's FrameXML.
- **Forever specifics.** Forever is a custom client, not a Blizzard
  product: its branch in wow-ui-source is maintained alongside the
  official ones, and major ecosystem projects ship Forever builds
  (EllesmereUI, RGX-Framework in beta, LibMasterAddons' `isForever`
  client flag, Ace3's 16001 interface line). Expect the 1.12-era API
  shape with Forever-specific deltas; verify against the `forever`
  branch, not against Era documentation.
- **The 3.80.x "Timewalking" client** realigned much of the Classic
  API toward Retail in April 2026 — addons ported from older Classic
  need the API-changes comparison, not assumptions (docs/11).

## Working multi-flavor

- Branch or guard flavor-specific code paths; detect the client by
  interface version (`select(4, GetBuildInfo())` is the standard
  runtime check) rather than by addon name hacks.
- Test on each target client (or in wowless with the matching product,
  [`08`](08-testing-and-debugging.md)). A green test on Retail says
  nothing about Era or Forever.

# 05 — Libraries and Frameworks

## LibStub — the mechanism underneath most of them

LibStub is a small versioning registry: libraries register themselves
by name (`LibStub("AceAddon-3.0")`), and every addon on a machine
shares the newest loaded copy. Two distribution models exist:

- **Embedded** — the addon carries its own copy of the library files
  (usually under `Libs/`), pulled in at packaging time by `.pkgmeta`
  externals ([`09`](09-packaging-and-distribution.md)). This is the
  Ace3 and LibMasterAddons model.
- **Standalone dependency addon** — the library is its own addon and
  consumers declare it in `## Dependencies:`. This is the RGX and
  Foundry model; the user must have it installed.

## Ace3 — the standard framework

- **Home:** https://github.com/WoWUIDev/Ace3 (development mirror).
  **Packaging authority:** Ace3's own README states the WoWAce SVN —
  `https://repos.wowace.com/wow/ace3/trunk` — is the primary source and
  what `.pkgmeta` externals should reference.
- **What it is:** 14 small, independently usable modules, each a
  LibStub library. Embed only the ones you use:
  AceAddon-3.0 (lifecycle), AceEvent-3.0, AceBucket-3.0 (event
  batching), AceTimer-3.0, AceHook-3.0, AceDB-3.0 (SavedVariables +
  profiles), AceDBOptions-3.0, AceConfig-3.0 + AceGUI-3.0 (options
  UI), AceConsole-3.0 (slash commands/chat), AceComm-3.0 +
  AceSerializer-3.0 (addon comms), AceLocale-3.0, AceTab-3.0 — plus
  the shared CallbackHandler-1.0 and LibStub, which ship in-tree.
- **Flavor support is real and current:** Ace3's own `.toc` declares
  Era 11508/11509, Forever 16001, TBC 20505/20506, Wrath 30405,
  Timewalking 38002, Cata 40402, MoP 50503/50504, and Retail
  120100–120107. One codebase spans every flavor in
  [`04`](04-flavors-and-interface-numbers.md).
- **Use it when:** almost always, for a new addon of any size. It is
  the ecosystem's default answer for lifecycle, events, DB/profiles,
  and options.

## RGX-Framework — the standalone alternative

- **Home:** https://github.com/RGXMods/RGX-Framework (also on
  WoWInterface and CurseForge).
- **What it is:** a modern, self-contained framework shipped as **one
  shared dependency addon** — events, timers, hooks, slash commands,
  minimap buttons, options panels, database profiles, DataBroker,
  media, dropdowns, UI controls, and a visual design system. Consumers
  declare `## RequiredDeps: RGX-Framework` and define the addon with a
  single declarative `RGXAddon "MyAddon" { ... }` call; deliberately
  **not** LibStub ("no LibStub bloat, no fallbacks" is their pitch).
  Advertises Retail, Classic Era, TBC, Wrath/Titan, Cata, MoP Classic,
  and WoW Forever (beta).
- **Status caveat:** actively developed (v2.18.3, Nov 2026) but very
  young and small — 1 GitHub star, and its WoWInterface page lags its
  GitHub releases. MIT per its WoWInterface page.

## LibMasterAddons — Classic-focused, single file

- **Home:** CurseForge only —
  https://www.curseforge.com/wow/addons/lib-master-addons. There is
  **no GitHub repository**; do not go looking for one.
- **What it is:** a lightweight framework for Classic-family addons: an
  addon container with **dependency injection** (Services/Views/Models
  by name — `CreateService`/`GetService` etc.), client detection
  (per-flavor flags including `isForever`, plus a `compat` shim mapping
  missing Classic globals to modern replacements), built-in services
  for logging, locales, timers, player names, chat output, and version
  checks, and a full UI toolkit rendered in Flat and Classic styles.
  Supports Era, Season of Discovery, Anniversary, Forever, TBC, Wrath,
  Titan Reforged, Cata, and MoP Classic.
- **Distribution quirk:** it **is** a LibStub library
  (`LibStub("LibMasterAddons-1.0")`) but ships as **one compiled .lua
  file** (currently `LibMasterAddons-1.1.17.lua`) that each addon
  embeds in its own `libs` folder. Updating = new file + one `.toc`
  line. Players never install it standalone.

## Foundry — the native-first newcomer

- **Home:** https://github.com/Royaleint/Foundry; CurseForge project
  "Foundry: Modern Addon Library and Ace3 Alternative".
- **What it is:** a small library that wraps Blizzard's *modern*
  toolkit instead of recreating it — the Settings API, the new menu
  system (Blizzard_Menu), ScrollBox, modern tooltip hooks
  (TooltipDataProcessor). Nine modules: Commands, Events, Lifecycle,
  DB (profiles — and it reads existing AceDB save files unchanged),
  List, Settings, Tooltip, Menu, Window, each mapped to an Ace3
  equivalent where one exists, designed for incremental adoption
  alongside Ace3. Distributed as a standalone library addon
  (`Foundry-1.0`); declare `## Dependencies: Foundry-1.0`. Supports
  Retail, Classic Era, TBC Anniversary, MoP Classic, and WoW Forever.
- **Status caveat:** brand new and tiny (repo created 2026-05-30,
  0 stars, actively pushed). "Ace3 alternative" is its own tagline,
  not an established position. MIT.

## WeakAuras — a reference, not a framework

WeakAuras2 (https://github.com/WeakAuras/WeakAuras2) is a standalone
end-user addon for customizable on-screen displays — **not** an
embeddable library; other addons do not build on it the way they build
on Ace3. It is actively maintained (5.22.1, Oct 2026; repo pushed
2026-11-16 — claims that it is archived are wrong). Its value to
authors is as a large, mature codebase to *read* for advanced
UI/trigger engineering, and as an integration surface from inside
WeakAuras itself (custom triggers).

## Choosing

| Need | Default answer |
|---|---|
| General-purpose framework, any flavor | Ace3 (embedded modules) |
| Classic-family app with DI structure and a bundled UI toolkit | LibMasterAddons (embed the single file) |
| Declarative all-in-one with a design system, users accept a dependency addon | RGX-Framework |
| Retail-modern Settings/menus with minimal surface | Foundry (watch its maturity) |
| Aura/trigger displays | WeakAuras (as a user) — not a dependency |

# 06 — Tools and Editors

## Editors and IDEs

### VS Code — the common setup, with a name trap

Two different extensions are constantly conflated:

- **WoW Bundle** (`Septh.wow-bundle`, by **Septh**) — WoW-flavored Lua
  5.1 grammar, `.toc` grammar/colorization, snippets, themes. **Its
  GitHub repo is archived; last release v1.3.0 (2018); its API data
  targets WoW 8.0.1.** Installable from the Marketplace, but treat its
  API knowledge as historical. It is grammar/highlighting only — no
  language server.
- **WoW API** (`ketho.wow-api`, by **Ketho**) — the maintained
  companion for the Lua language server (LuaLS): WoW API annotations
  for completion and diagnostics. Pushed Oct 2026. This, plus a Lua
  language-server extension, is the current VS Code route.
- **EmmyLua** (`tangzx.emmylua`, by Tangzx) — a general Lua language
  extension (completion, debugging, analysis) used in both VS Code and
  JetBrains IDEs. Not WoW-specific; WoW knowledge comes from stub files
  (below).

### AddOn Studio — the dedicated IDE

https://addonstudio.org/ — a full IDE on the Visual Studio Shell
(editions named 2022 / 2015 / 2010; same WoW features in each). Visual
drag-and-drop FrameXML designer, IntelliSense for WoW
functions/events, FrameXML schema validation, cross-file IntelliSense
that respects `.toc` load order, automatic `.toc` generation/metadata
editing, deployment to multiple WoW installs, Git/SVN integration, a
Blizzard resource browser, a built-in Lua console, and WoWBench
support (historical). States support for Retail and Classic. Pick the
2022 edition if unsure; expect it to manage the `.toc` for you.

### ZeroBrane Studio — general Lua IDE

https://studio.zerobrane.com/ — lightweight, cross-platform, written
in Lua; current (v2.01). Completion, live coding, analyzer, remote
debugger for Lua 5.1–5.4/LuaJIT. **No WoW API knowledge built in** —
its WoW value is editing and debugging plain Lua logic outside the
client.

### IntelliJ IDEA — EmmyLua + stubs

The canonical stub project is
**Ellypse/IntelliJ-IDEA-Lua-IDE-WoW-API**: WoW API documentation/stubs
formatted for the EmmyLua plugin (JetBrains plugin ID 9768), partly
generated from Blizzard's own API documentation files. Setup: install
EmmyLua, clone the stubs (often alongside a wow-ui-source checkout),
register the folders as Lua libraries. Caveat: the stubs are **stale**
(last pushed Jan 2024) — completion will lag current patches.
Community guides recommend the original EmmyLua plugin over "EmmyLua2"
for WoW work (proven 5.1 support).

## In-game development tools

- **WowLua** (WoWInterface info7366; also CurseForge) — in-game Lua
  interpreter + multi-page script editor by James Whitehead II (the
  *WoW Programming* author); `print()` goes to its window. `/wowlua`
  or `/lua`, run pages with `/wowluarun`. Maintained (updated Apr
  2026). A 1.12-client fork exists (laytya/WowLuaVanilla).
- **Lua Browser** (CurseForge / WoWInterface, by Aezay) — folder-style
  browser of the live Lua environment (tables, widgets) for
  inspection. **Dormant** — last updated Oct 2020. `/lb`, `/luabrowser`.
- **DevTool** (https://github.com/brittyazel/DevTool) — debugger-like
  in-game inspection of tables, events, and function calls in a
  columnar UI; the richer alternative to `print()`/`/dump`. API:
  `DevTool:AddData(data, "name")`; slash commands `/dev`,
  `/dev eventadd <event> [unit]`, `/dev logfn <fn> <parent>`. Repo is
  **archived** on GitHub (latest release 1.3.0, Jan 2026) — usable,
  unmaintained. It is **not** a packaging tool.

## Headless testing

**wowless** — https://github.com/wowless/wowless (not
`lua-wow/wowless`; that URL does not exist). A headless WoW client Lua
and FrameXML interpreter for testing addons without the game: it
implements WoW's taint/security model via a vendored Lua 5.1 fork
("elune"), with API specs in YAML generated from Blizzard's API
documentation, across multiple game products/flavors. Built from
source (Docker/devcontainer, CMake; no GitHub releases); run an addon
with its `run` command, a product flag, and `--addondir`. Do not point
a stock `lua`/`luajit` at it — its runtime differs on purpose.
Actively maintained (pushed 2026-11-16).

**WowBench** is its defunct 2006-era ancestor (WoWInterface files it
under "Discontinued and Outdated Mods") — historical interest only.

## Game-data tools (finding IDs, files, models)

- **wow.tools is dead** — the site shut down in May 2025 and its front
  page is a retirement notice. Do not cite it as a live resource.
- **wago.tools** — the online successor for part of the former
  wow.tools functionality (DB2/file exploration from the Wago team).

# 07 — Textures and Art

## The BLP format

Custom addon textures ship as **BLP** (Blizzard's texture format;
TGA is also accepted by the client for addon textures). BLP comes in
variants (BLP1/BLP2; paletted, raw, DXT-compressed, and JPEG-encoded),
and the client is particular about which variants it accepts — which
is why conversion tooling matters and why "it converted" is not the
same as "it loads".

## The three tools named "BLPConverter" — disambiguation

"BLPConverter" is the name of at least **three unrelated tools**.
Always say which one you mean:

| Tool | Where | What | Status |
|---|---|---|---|
| BLPConverter.exe (classic) | WoWInterface info14110 | Windows CLI converter (BLP↔PNG) focused on precise control of the exact BLP format produced; built for batch scripts | Old; download page live, no current maintenance signal (**Unverified** beyond the page being up) |
| Kanma/BLPConverter | github.com/Kanma/BLPConverter | C++ CLI (BLP→PNG/TGA), BLP1 + BLP2 incl. RAW3, macOS/Linux, MIT | Stale (bundles old libsquish/FreeImage) |
| Kkthnx/BLPConverter | github.com/Kkthnx/BLPConverter | Modern desktop app (Tauri 2, Win/Linux/macOS): two-panel drag-and-drop BLP↔PNG, batch/folder conversion, PNG→BLP with RAW/DXT1/DXT3/DXT5, mipmaps, power-of-two validation | Current (2026) |

**Blpc** (WoWInterface info18810) is a separate tool: a graphical
Blp2 viewer/converter in C# with source included, batch conversion,
automatic power-of-two resizing, and a reusable `cBlp2` class for
other projects. Legacy (.NET Framework 4.0 era). Known gap:
**JPEG-encoded BLP textures are not implemented** in Blpc.

## Practical rules

- Textures referenced from Lua/XML use paths relative to the game's
  `Interface\` root (e.g. `Interface\AddOns\MyAddon\Media\icon`) —
  historically **without the file extension** in texture strings.
- Dimensions must be powers of two per side for classic-era clients;
  the modern converters validate this — use that check.
- Blizzard's own artwork can be browsed in the exported client files
  (`wow-ui-source`, and the game-data tools in
  [`06`](06-tools-and-editors.md)). The old **WoW Programming Art
  Browser** at wowprogramming.com/utils/artbrowser is **dead** (404);
  do not link it.
- Icon and texture IDs for spells/items come from the game-data tools
  (wago.tools / wow.tools.local), not from guessing.

# 08 — Testing and Debugging

## In the client

- **Turn script errors on.** A Lua error with errors hidden is a
  silent dead feature. `/console scriptErrors 1` (and keep the
  error display enabled while developing).
- **`/dump`** evaluates and pretty-prints a value in chat — the
  zero-install inspection tool.
- **`/reload`** reloads the UI: the basic edit-test loop. Remember
  SavedVariables only persist across a real logout/reload cycle as
  declared in the `.toc`.
- **DevTool** ([`06`](06-tools-and-editors.md)) for structured
  inspection: watch tables live, log events as they fire, trace
  function calls — the debugger-shaped alternative to sprinkling
  `print()`.
- **WowLua** for trying API snippets against the live environment
  before committing them to addon code — the fastest way to check "is
  this function real on *this* client" (AGENTS.md rule 1).

## Headless / CI testing

**wowless** (https://github.com/wowless/wowless) loads an addon in a
simulated client — Lua + FrameXML interpreted, taint/security model
implemented — so load errors, event wiring, and pure-logic behavior
can be tested in CI without a game install, per product/flavor.
Build it from source (Docker/devcontainer), then run with the product
flag and `--addondir path/to/YourAddon`. Its test suite style
(luassert specs) is the model for addon-side tests. What headless
testing cannot prove: real rendering, real performance, and anything
needing the actual game world — label those **Unverified** until run
in the target client.

## Taint hunting

Symptoms: "Interface action failed because of an AddOn", blocked
protected calls in combat, secure frames misbehaving after your addon
loads. Method:

1. Reproduce with **only** your addon enabled.
2. Check the usual sources: writing into Blizzard frames' fields,
   hooking secure functions insecurely, modifying unit frames or
   action buttons outside secure templates, leaking globals
   ([`02`](02-lua-in-wow.md), [`03`](03-api-events-and-widgets.md)).
3. Fix by restructuring (secure templates, `hooksecurefunc` used
   correctly, no mutation of secure state), never by suppressing the
   error display.

## The test matrix that matters

- [ ] Loads clean on the **target flavor's** client, correct
      `## Interface:` ([`04`](04-flavors-and-interface-numbers.md))
- [ ] First run with no SavedVariables; second run with existing ones;
      run with SavedVariables from the *previous addon version*
- [ ] Combat: enter combat and exercise every protected-adjacent
      feature (taint check)
- [ ] `/reload` mid-session; logout/login; character switch
      (per-character variables)
- [ ] With the addons your users will run alongside (a big Ace3 addon,
      a UI suite) — global collisions and load order only show up in
      company
- [ ] Performance sanity: no heavy work in unthrottled `OnUpdate`
      handlers; large SavedVariables stay reasonable

# 09 — Packaging and Distribution

## Blizzard's UI Add-On Development Policy (the rules that bind everyone)

Canonical home: the Blizzard forum thread "UI Add-On Development
Policy" (US: https://us.forums.blizzard.com/en/wow/t/ui-add-on-development-policy/24534/1;
EU equivalent exists). Originally released 2009-03-20; still the
posted policy. Its 8 rules, in substance:

1. Add-ons must be **free of charge** — no charging, no premium
   versions.
2. Add-on code must be **completely visible** — no hiding or
   obfuscation.
3. Add-ons must not negatively impact realms or other players.
4. Add-ons may not include **advertisements**.
5. Add-ons may not **solicit donations** in-game.
6. Add-ons must not contain offensive or objectionable material.
7. Add-ons must abide by the WoW Terms of Use and EULA.
8. Blizzard may disable add-on functionality as it sees fit.

Developer contact named in the policy: WoWUI@blizzard.com. (Custom
clients such as WoW Forever are outside Blizzard's policy scope, but
rules 1–2 and 4–5 are also this repo's house style for every flavor.)

## The BigWigs packager — the standard release route

- **Repo:** https://github.com/BigWigsMods/packager — actively
  maintained (v2.7.0, Nov 2026).
- **What it does:** `release.sh` builds a distributable addon zip from
  a Git/SVN/Hg checkout and can upload it to **CurseForge,
  WoWInterface, Wago, and GitHub (as a release)** in one run. Version
  comes from the VCS tag on HEAD; the changelog is generated from
  commits since the previous tag; files are staged into `.release/`;
  externals are fetched; keyword and localization substitutions are
  applied.
- **Invocation:** run `release.sh` in the checkout, or use the GitHub
  Action `BigWigsMods/packager@v2`.
- **Project IDs:** flags `-p` (CurseForge), `-w` (WoWInterface), `-a`
  (Wago) — or declare them in the `.toc` as `## X-Curse-Project-ID:`,
  `## X-WoWI-ID:`, `## X-Wago-ID:`. The package name comes from the
  `.toc` file name.
- **`.pkgmeta` directives** (the ones that matter): `externals` (pull
  libraries like Ace3 from their repos at build time — for Ace3,
  reference the WoWAce SVN per [`05`](05-libraries-and-frameworks.md)),
  `ignore`, `plain-copy`, `license-output`, `manual-changelog`,
  `move-folders`, `package-as`, `enable-nolib-creation` (nolib builds
  upload only to GitHub releases), `enable-toc-creation`,
  `required-dependencies`, `optional-dependencies`, and the
  WoWInterface options (`wowi-archive-previous`, `wowi-create-changelog`,
  `wowi-convert-changelog`).
- **Multi-flavor TOCs:** the packager supports multiple `## Interface:`
  values and per-flavor `.toc` files, and with `-S` (or
  `enable-toc-creation: yes`) it *generates* per-game-type TOCs from
  `## Interface-[Type]:` lines in one master `.toc` — the clean way to
  ship Retail + Era + Forever from one tree
  ([`04`](04-flavors-and-interface-numbers.md)).
- **Substitutions:** `@project-version@`, `@file-hash@`, localization
  blocks `@localization(...)@`, and build-type comment keywords
  (`@alpha@`, `@debug@`, `@do-not-package@`, `@version-retail@`,
  `@version-classic@`, …) that include/strip code per build.

## Manual packaging (when the packager doesn't fit)

Zip the addon folder itself (folder name = addon name, `.toc` inside
at the folder root — not nested one level deeper; the classic broken
release). Name the archive with the addon name and version. This is
also the shape used for direct GitHub-release distribution of
single-flavor addons.

## Where addons are distributed

- **CurseForge** — the largest addon host; packager uploads natively.
- **Wago** (wago.io addons) — packager uploads natively.
- **WoWInterface** — the oldest author community + host; packager
  uploads natively.
- **GitHub Releases** — direct distribution; the packager can publish
  there too. House standard for releases here: the addon zip plus
  `SHA256SUMS.txt`, with README/description/topics kept current and
  screenshots from real runs.

## Release discipline

- Tag the release in git; the tag *is* the version the packager ships.
- Changelog entries are factual product documentation only.
- Every release re-checks: `.toc` interface numbers for every flavor
  shipped, the four addon docs (README/FEATURES/DESCRIPTION/CHANGELOG),
  and that embedded libraries are the versions `.pkgmeta` declares.

# 11 — AI-Assisted Addon Development

AI help on WoW code fails in predictable ways, and this repo exists to
counter them. The EsfandTV/ThePrimeagen stream (Oct 2026,
[`10`](10-communities-and-learning.md)) showed a complete beginner
shipping working WoW Forever addons in a day with AI assistance — the
workflow works when the ground truth is enforced.

## The failure modes

- **Invented APIs.** The WoW API is huge, versioned, and flavor-split;
  a model will produce confident, plausible function names that do not
  exist on the target client. Counter: AGENTS.md rule 1 — every call
  traced to the wiki, the matching wow-ui-source branch, or `/api`.
- **Flavor bleed.** Training data mixes 20 years of clients: a Retail
  namespace in an Era addon, an Era interface number in a Forever
  `.toc` (Forever is **16001**), a modern template on a 1.12-lineage
  client. Counter: flavor first, and check the flavor's own sources.
- **Modern Lua.** Models default to current Lua idioms; WoW is a 5.1
  subset ([`02`](02-lua-in-wow.md)).
- **Stale sources quoted as current.** Wowpedia-Fandom (frozen 2023),
  wowprogramming.com (frozen ~2015), awesome-wow (2019), and archived
  editor extensions all rank well in search results. Counter: the
  ground-truth hierarchy in the README.
- **Secure-code guesses.** Taint and protected-function rules are
  unforgiving and under-documented in training data. Counter:
  [`03`](03-api-events-and-widgets.md) + secure templates copied from
  Blizzard's own modules, not invented.

## Existing AI tooling for WoW development

- **Xerrion/wow-addon-skills** — https://github.com/Xerrion/wow-addon-skills —
  an OpenCode configuration pack: an agent definition
  (`agents/wow-addon.md`), a wow-addon skill whose research references
  cover addon design, event handling, the frame API, Lua patterns, and
  a research toolkit, plus a working **MCP server** with tools for WoW
  API lookup, Blizzard source browsing, event info, and wiki fetching.
  Recent and small (pushed Nov 2026). This is AI-workflow tooling —
  nothing in it loads in the game client.
- **liuwu0623/wow-addon-dev** — https://github.com/liuwu0623/wow-addon-dev —
  a single SKILL.md pack for creating, migrating, and fixing addons
  for the **3.80.1 "Timewalking" Classic client** (the April 2026
  client whose API was aligned heavily toward Retail). Its references
  include an API-changes comparison for 3.80.1, an API quick
  reference, events, secure action buttons, and WoW UI source notes,
  plus a complete starter addon template. Repo description is in
  Chinese; small and quiet since Apr 2026.
- **This repo** — point the agent at `AGENTS.md` first, then the doc
  for the task. The rules there (never invent, flavor first, 5.1 only,
  verify or label Unverified) are the contract the resources above
  assume.

## Working rules for AI-assisted sessions

1. State the target flavor and interface number in the first message
   of the work, and keep it in the `.toc` from the first commit.
2. Give the agent the ground-truth sources (wiki flavor page,

3. Verify generated code by loading it in the target client (or
   wowless) before building on it — AI code that has never been loaded
   is a hypothesis.
4. Keep the human's four addon docs (README/FEATURES/DESCRIPTION/
   CHANGELOG) factual; generated marketing copy in public docs is a
   defect.

# 12 — Patterns Cookbook

The recurring shapes of addon code, each small enough to copy and
adapt. All of these appear in the [`../templates/`](../templates/)
and [`../examples/`](../examples/) — this doc explains them.

## The namespace header

Every Lua file starts with the same line. The client passes the addon
name and one shared table to every file in the addon:

```lua
local addonName, addon = ...
```

State shared between files lives on `addon`. Nothing else needs to be
a global.

## The event frame

One hidden frame receives events; its `OnEvent` branches by name:

```lua
local frame = CreateFrame("Frame")
frame:RegisterEvent("PLAYER_ENTERING_WORLD")
frame:SetScript("OnEvent", function(self, event, ...)
    -- branch on `event`; payload rides in `...`
end)
```

Rules: register only what you handle; `ADDON_LOADED` fires for every
addon, so filter its first payload value against your own name;
unregister one-shot events after use.

## SavedVariables init with defaults

SavedVariables exist (possibly as `nil`) by the time your
`ADDON_LOADED` fires. Merge defaults *by missing key only*, so user
changes are never overwritten on upgrade:

```lua
local defaults = { enabled = true, counter = 0 }

local function ApplyDefaults(db, defs)
    for k, v in pairs(defs) do
        if db[k] == nil then db[k] = v end
    end
    return db
end

-- inside the ADDON_LOADED handler:
MyAddonDB = ApplyDefaults(MyAddonDB or {}, defaults)
```

(Nested tables need a recursive merge; AceDB — docs/05 — does this
for you, which is one reason it is the default.)

## Slash commands

Two globals register a command; keep the handler thin:

```lua
SLASH_MYADDON1 = "/myaddon"
SLASH_MYADDON2 = "/ma"
SlashCmdList["MYADDON"] = function(msg)
    -- parse msg, call into your addon's functions
end
```

The `SLASH_<KEY>n` names and the `SlashCmdList` key must use the same
KEY. AceConsole (docs/05) wraps this with argument parsing.

## Throttled OnUpdate

`OnUpdate` runs **every frame**. Never do real work in it directly —
accumulate elapsed time and work at an interval:

```lua
local elapsed = 0
frame:SetScript("OnUpdate", function(self, dt)
    elapsed = elapsed + dt
    if elapsed < 0.2 then return end
    elapsed = 0
    -- periodic work here, at most 5x per second
end)
```

Better still: prefer events over polling (docs/13). `OnUpdate` is the
last resort, for things no event announces.

## Splitting work across frames

A loop over thousands of items in one call freezes the UI. Process a
slice per frame and resume next frame until done — the pattern every
scanner/indexer addon uses. Keep the per-frame slice small and the
state (cursor position) on the addon table so the work is resumable
and cancellable.

## The localization table

One table, one file per locale, English as the fallback (full
treatment in [`14-localization.md`](14-localization.md)):

```lua
local _, addon = ...
addon.L = addon.L or {}
local L = addon.L
L["Reset position"] = "Reset position"  -- enUS defaults
```

Code always looks text up in `L`; it never hard-codes display strings.

## Reading state safely at load

Do not touch other addons' frames, the player's unit data, or
SavedVariables at file scope (top level) — at file-execution time
almost nothing exists yet. File scope is for definitions; everything
that reads the world waits for `ADDON_LOADED` / `PLAYER_LOGIN`.

# 13 — Performance and Memory

An addon runs inside the game's frame loop, on the player's machine,
next to every other addon they own. Being a good citizen is a feature.

## The frame budget

Every frame, the client runs all UI code and still has to render.
Work you do in an event handler or `OnUpdate` is time taken from that
frame. The practical rules:

- **Events over polling.** Register for the event that announces the
  change instead of checking for it every frame. `OnUpdate` is the
  last resort, always throttled (pattern in
  [`12-patterns-cookbook.md`](12-patterns-cookbook.md)).
- **High-frequency events are a cost center.** Unit events
  (`UNIT_HEALTH` family) and combat-log events can fire hundreds of
  times a second in a raid. Register narrowly (`RegisterUnitEvent`
  for the units you need), keep handlers allocation-free, and
  consider **AceBucket-3.0** (docs/05), which coalesces bursts of the
  same event into one call at an interval you choose.
- **Split big jobs across frames.** Indexing, scanning bags/banks,
  and rebuilding large lists must be sliced (docs/12) — a 200 ms
  hitch is a visible freeze and it is yours.
- **Cache in locals.** Global lookups and repeated table indexing in
  hot paths add up; hoist `pairs`, `math.floor`, and your own hot
  functions to file-scope locals.
- **Don't create garbage in hot paths.** Throwaway tables and string
  concatenation in per-frame code feed the garbage collector, which
  bills everyone. Reuse scratch tables; build strings once.

## Measuring

- **Memory:** `UpdateAddOnMemoryUsage()` then
  `GetAddOnMemoryUsage("AddonName")` (KB) — long-standing API
  functions, also what most in-game performance panels display.
- **CPU:** enable the script profile CVar (`/console scriptProfile 1`,
  then `/reload`) and read `GetAddOnCPUUsage("AddonName")` /
  `UpdateAddOnCPUUsage()`. Profiling changes timings; measure with it
  on to *compare*, not to quote absolute numbers.
- **In practice:** test in the busiest environment your users will
  hit (a full raid, a capital city), with the popular addons they run
  alongside yours — your addon never runs alone in the real world.

## SavedVariables hygiene

SavedVariables are loaded at login and written at logout, whole-table.
A database that grows forever (full history logs, per-item caches)
slows every login/logout for that player and bloats the file on disk.
Store what the features need, prune on a schedule (e.g. at
`ADDON_LOADED`, drop entries older than X), and keep transient state
in plain Lua tables that die with the session (example 02 shows the
split).

## The standing checks

- No unthrottled `OnUpdate` doing real work.
- No event registered "just in case".
- No string building or table creation inside combat-log or
  unit-event handlers on the hot path.
- Large scans are sliced across frames and cancellable.
- SavedVariables have a pruning story.

# 14 — Localization

## The shape of it

- All display text goes through one table (`L`), looked up by the
  English source string. Code never hard-codes display strings.
- One file per locale under `Locales/`, loaded from the `.toc` before
  the code that uses the strings; the English (enUS) file loads first
  and defines the fallback for every key.
- The client's locale is `GetLocale()` (e.g. `"enUS"`, `"deDE"`,
  `"frFR"`). Locale files early-exit when they are not the active
  locale:

```lua
local _, addon = ...
if GetLocale() ~= "deDE" then return end
local L = addon.L
L["Reset position"] = "Position zurücksetzen"
```

## With AceLocale-3.0

Ace3's locale module (docs/05) formalizes the same pattern:
`NewLocale(addonName, "deDE")` returns the table to fill (or `nil`
when that locale is inactive, so the file does nothing);
`NewLocale(addonName, "enUS", true)` marks the default locale, and
`GetLocale(addonName)` hands the active table to your code. Its
default-locale fallback means an untranslated key shows the English
string instead of an error — the behavior you want.

## Rules that keep translations working

- **Keys are full sentences, not fragments.** Word order differs by
  language; never assemble a sentence from translated pieces.
- **Placeholders travel with the string.** Use `string.format`
  placeholders (`%s`, `%d`) inside the translated string and format
  after lookup — translators can then reorder them as their grammar
  needs.
- **Don't translate keys that aren't display text** (event names,
  internal IDs, saved-variable keys). Translating a data key breaks
  the data.
- **New strings land in enUS first.** A key missing from enUS is a
  bug; a key missing from deDE is a fallback.
- Keep a note in the repo of which locales are complete, partial, or
  machine-only — translators (often users volunteering on the addon
  host) work from that list.

## Testing a locale you don't read

- Switch the client locale if your installation supports it, or
  temporarily force the locale file to load by removing its
  `GetLocale()` guard in a test build.
- Check the longest strings in your UI: German and Russian routinely
  overflow layouts sized for English. Frames should size to text or
  truncate cleanly (see the layout rules in the checklist).

# Reference — Common Events (starter subset)

The events nearly every addon touches, with their payload shape.
**This is a starter subset, not the full list** — the complete,
per-flavor event list lives on Warcraft Wiki's Events page, and event
availability/payloads change between flavors and patches. Verify
there before relying on any event (AGENTS.md rule 1).

| Event | Payload | Fires when |
|---|---|---|
| `ADDON_LOADED` | addon name | An addon's files finish loading. Fires for *every* addon — filter on the name. The moment to initialize SavedVariables. |
| `PLAYER_LOGIN` | — | The player has logged in and all addons are loaded. |
| `PLAYER_ENTERING_WORLD` | isInitialLogin, isReloadingUi | The player enters the world (login, reload, zoning into an instance). |
| `PLAYER_DEAD` | — | The player dies. |
| `PLAYER_ALIVE` | — | The player is alive again (released or resurrected out of ghost form distinctions apply — check the wiki for your flavor). |
| `PLAYER_LEVEL_UP` | new level, plus stat gains | The player gains a level. |
| `PLAYER_LOGOUT` | — | Logout begins — the last chance to tidy state before SavedVariables are written. |
| `VARIABLES_LOADED` | — | SavedVariables have been loaded (early; per-addon `ADDON_LOADED` is usually the better hook). |
| `UI_ERROR_MESSAGE` | error type, message | The client shows an error message (e.g. "Out of range"). Payload shape varies by client generation — verify per flavor. |
| `CHAT_MSG_ADDON` | prefix, message, channel type, sender | An addon message arrives (registered prefixes only — see the addon comms notes in docs/05, AceComm). |

## Handling rules

- Register only for events you handle; unregister one-shot events
  (`ADDON_LOADED` for your own addon) once consumed — see the pattern
  in [`../docs/12-patterns-cookbook.md`](../docs/12-patterns-cookbook.md).
- Unit events (`UNIT_HEALTH` and family) require a unit token and
  fire at high frequency — register with `RegisterUnitEvent` and read
  [`../docs/13-performance-and-memory.md`](../docs/13-performance-and-memory.md)
  before using them.
- Combat-log data arrives through `COMBAT_LOG_EVENT_UNFILTERED` with
  a large sub-event payload; its exact shape is flavor-sensitive —
  the wiki's Combat Log page is the reference.

# Reference — Interface Numbers

The quick table. Full discussion:
[`../docs/04-flavors-and-interface-numbers.md`](../docs/04-flavors-and-interface-numbers.md).
Machine-readable form: [`../tools/interface-numbers.json`](../tools/interface-numbers.json).
Checked 2026-11-17 against the Ace3 project's `.toc` and the
`Gethe/wow-ui-source` branch list.

| Flavor | Interface | wow-ui-source branch |
|---|---|---|
| Retail | 120100–120107 | `live` |
| Classic Era | 11508, 11509 | `classic_era` |
| WoW Forever | **16001** | `forever` |
| TBC Classic | 20505, 20506 | `classic` |
| Wrath Classic | 30405 | `classic` |
| Classic "Timewalking" 3.80.x | 38002 | `classic` |
| Cata Classic | 40402 | `classic` |
| MoP Classic | 50503, 50504 | `classic` |

## Find your client's number in-game

```
/run print(select(4, GetBuildInfo()))
```

`GetBuildInfo()` returns version, build, date, and the interface
number — the fourth value is the exact number your `.toc` needs.
Run it on the actual client you target; never copy a number from a
different flavor's addon, a forum post, or this table without
checking, because clients patch and numbers move.

- A `.toc` whose `## Interface:` doesn't match the client = the addon
  is marked out of date and does not load (no error, just silence).
- Forever is **16001**, always. Era numbers in a Forever `.toc` are
  the single most common dead-addon cause on that client.
- One release can serve several flavors: per-flavor `.toc` files, or
  the BigWigs packager generating them from `## Interface-[Type]:`
  lines ([`../docs/09-packaging-and-distribution.md`](../docs/09-packaging-and-distribution.md)).

# Reference — Library Directory

The shared-library ecosystem an addon author actually meets. All of
these are **LibStub** libraries unless noted: they register by name,
and every addon on a machine shares the newest loaded copy
([`../docs/05-libraries-and-frameworks.md`](../docs/05-libraries-and-frameworks.md)).

| Library | What it is for | Where it lives |
|---|---|---|
| **LibStub** | The versioning registry itself. Ships inside the Ace3 tree; also embedded standalone by most library-using addons. | WoWAce SVN / Ace3 tree |
| **CallbackHandler-1.0** | Callback/event dispatch used by AceEvent and friends. Ships inside the Ace3 tree. | WoWAce SVN / Ace3 tree |
| **Ace3 modules** (AceAddon, AceEvent, AceDB, AceConfig, AceGUI, AceConsole, AceComm, AceSerializer, AceLocale, AceTimer, AceBucket, AceHook, AceDBOptions, AceTab — all `-3.0`) | The standard framework; embed only the modules you use. Full treatment in docs/05. | WoWAce SVN is the `.pkgmeta` authority; GitHub WoWUIDev/Ace3 is the dev mirror |
| **LibDataBroker-1.1 (LDB)** | A data-broker spec: addons publish feeds/buttons that display addons (panels, minimap launchers) render. RGX-Framework and many addons expose LDB objects. | CurseForge / WoWInterface library listings |
| **LibDBIcon-1.0** | Puts an LDB object on the minimap as a draggable button — the standard minimap-button mechanism. LibMasterAddons uses it optionally for exactly this. | CurseForge / WoWInterface library listings |
| **LibMasterAddons-1.0** | Classic-family framework (dependency injection, locales, timers, UI toolkit) shipped as one embeddable file. Docs/05. | CurseForge only — no GitHub repo |

## Embedding rules (all libraries)

- Embed at packaging time with `.pkgmeta` externals
  ([`../docs/09-packaging-and-distribution.md`](../docs/09-packaging-and-distribution.md));
  do not paste library source into your repo by hand — it goes stale
  silently.
- Load order in the `.toc`/`embeds.xml`: LibStub, then
  CallbackHandler, then everything else.
- Never ship a *modified* embedded library under its real name —
  LibStub will hand your modified copy to other addons.

# Addon Release Checklist

Run against the addon tree and the **target client** before shipping.

## Targeting

- [ ] Target flavor named (Retail / Classic Era / progression Classic /
      WoW Forever) and `## Interface:` matches that client's current
      interface number (`docs/04-flavors-and-interface-numbers.md`).
      Forever is **16001** — never an Era number.
- [ ] Multi-flavor releases: per-flavor `.toc` files (or packager
      `## Interface-[Type]:` generation) each carry the right number.

## Code correctness

- [ ] Every WoW API function, event, and widget method in the code
      traces to Warcraft Wiki (target flavor), the matching
      wow-ui-source branch, or the in-game `/api` docs — no invented
      calls (`AGENTS.md` rule 1).
- [ ] Lua is 5.1-subset only: no `//`, no `goto`, no `table.unpack`,
      no 5.2+ library calls.
- [ ] SavedVariables / SavedVariablesPerCharacter declared in the
      `.toc` for every persisted global.
- [ ] No `SetBackdrop` on a plain frame — `BackdropTemplate` (or the
      mixin) everywhere a backdrop is set.
- [ ] No unlocalized globals beyond the addon namespace pattern.
- [ ] Libraries embedded the standard way (LibStub + `.pkgmeta`
      externals) or declared as dependencies — no pasted library code.

## In-client testing (`docs/08-testing-and-debugging.md`)

- [ ] Loads with script errors enabled and shows none.
- [ ] First run (no SavedVariables), repeat run, and run with the
      previous version's SavedVariables all work.
- [ ] Combat pass: protected-adjacent features exercised in combat
      with no taint errors / blocked actions.
- [ ] `/reload`, logout/login, and character switch behave.
- [ ] Runs alongside a major framework addon / UI suite without
      errors.
- [ ] Anything not actually run in the target client is recorded as
      **Unverified** in the release notes — not silently implied.

## Packaging (`docs/09-packaging-and-distribution.md`)

- [ ] Built with the BigWigs packager from a tagged checkout, or as a
      manual zip with the addon folder at the archive root.
- [ ] Archive named with addon name + version; `SHA256SUMS.txt`
      alongside for GitHub releases.
- [ ] Blizzard policy respected: free, code fully visible (no
      obfuscation), no ads, no in-game donation solicitation.

## Docs and metadata

- [ ] `README.md`, `FEATURES.md`, `DESCRIPTION.md`, `CHANGELOG.md`
      present and current; license file included.
- [ ] Changelog entry states the version's changes factually.
- [ ] Repo description and topics accurate for this release;
      screenshots are real captures from the target client.

# Debugging Checklist

When an addon misbehaves, in this order. Most "mystery" bugs are
steps 1–3.

## It doesn't load at all

- [ ] Folder name = `.toc` name, folder directly under
      `Interface/AddOns/` (not nested one level deeper).
- [ ] `## Interface:` matches the client exactly — check in-game:
      `/run print(select(4, GetBuildInfo()))`. Wrong number = silent
      no-load. Forever is 16001.
- [ ] The addon is enabled in the character-select addon list, and
      "load out of date addons" is not masking a wrong interface.
- [ ] Run [`../tools/check-addon.py`](../tools/) on the folder.

## It loads but errors

- [ ] Script errors are ON (`/console scriptErrors 1`) — with them
      off, failures are invisible.
- [ ] Read the *first* error, not the cascade: fix top-down, `/reload`
      between fixes.
- [ ] Every API call in the failing file verified against the target
      flavor's docs (AGENTS.md rule 1) — an invented or
      wrong-flavor function is the usual cause.
- [ ] No file-scope code reads the world (units, other addons,
      SavedVariables) before `ADDON_LOADED`.

## It works alone, breaks with other addons

- [ ] Global collision: search your code for unlocalized globals
      beyond the namespace pattern.
- [ ] Taint: does it write into Blizzard frames, hook secure
      functions insecurely, or touch action buttons outside secure
      templates? (docs/03, docs/08)
- [ ] Load order: a dependency you assumed is `OptionalDeps` but not
      guaranteed — guard or make it a hard dependency.

## It works until combat

- [ ] Protected call from tainted code: casting/moving/targeting and
      secure-frame changes are blocked in combat lockdown. Restructure
      to secure templates; never "fix" by hiding the error.

## Data is lost between sessions

- [ ] The variable is declared under `## SavedVariables` (or
      PerCharacter) in the `.toc` — undeclared means unsaved.
- [ ] You are writing to the *global* of that exact name, not a local
      shadow of it.
- [ ] The write happens before logout completes (writes at
      `PLAYER_LOGOUT` are fine; writes after are not).

## It's slow / causes hitches

- [ ] Unthrottled `OnUpdate` doing real work (docs/13).
- [ ] High-frequency events registered broadly instead of per-unit.
- [ ] A big loop (scan/index/rebuild) running in one call instead of
      sliced across frames.
- [ ] SavedVariables grown unbounded — check the file size on disk.

# Multi-Flavor Port Checklist

Porting an addon between Retail, Classic Era, the progression Classic
clients, and WoW Forever. Background: docs/04.

## Before writing code

- [ ] Target flavor named, with its current interface number from
      [`../reference/interface-numbers.md`](../reference/interface-numbers.md)
      (verified in-game with `GetBuildInfo()` on the target client).
- [ ] The matching `Gethe/wow-ui-source` branch identified
      (`live` / `classic_era` / `classic` / `forever`) and used as
      the API reference for the port — not the source flavor's docs.
- [ ] Every API function, event, and widget the addon uses checked
      for existence **on the target flavor** (wiki flavor pages +
      target branch). Make a list of the ones that don't exist —
      that list is the port.

## The usual gaps

- [ ] `C_*` namespaces: several Retail namespaces don't exist on
      Classic-family clients, and vice versa. Each call needs a
      target-side answer or a guard.
- [ ] Templates: the XML templates the UI uses (including backdrop
      behavior) differ per flavor — confirm each template exists in
      the target branch's FrameXML.
- [ ] Settings/options: Retail's modern Settings API has no direct
      equivalent on 1.12-lineage clients (Era/Forever) — plan an
      AceConfig or custom panel there.
- [ ] Events: names and payloads differ (combat log especially).
      Re-check every registered event on the target's Events page.
- [ ] Client detection at runtime uses the interface number
      (`select(4, GetBuildInfo())`), not addon-name or version-string
      hacks.

## Packaging the port

- [ ] Per-flavor `.toc` files, or one master `.toc` with
      `## Interface-[Type]:` lines for packager generation (docs/09).
- [ ] Flavor-specific code paths are guarded or branched — one tree,
      no copy-pasted sibling addons to drift apart.
- [ ] The port is loaded and exercised **on the target client** (or
      in wowless with the matching product). A green run on the
      source flavor proves nothing about the target; anything not run
      is recorded as Unverified.

[`../docs/04-flavors-and-interface-numbers.md`](../docs/04-flavors-and-interface-numbers.md);

  `embeds.xml` load order (LibStub first) is the part that must not
  change.
- Delete the modules you do not use from **both** `.pkgmeta` and
  `embeds.xml` — they must stay in sync.
